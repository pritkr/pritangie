## 020 superseded — view transition is now a push, not a wipe

The wipe specified in `020` was implemented and then replaced. Two problems
with it in practice:

- `::view-transition-old(root) { animation: none }` froze the outgoing page as
  a **fully-opaque photograph** for the whole 200ms while a sheet slid over it.
  The old page never participated in the motion, so it read as a slide deck
  rather than navigation.
- The header was part of the root snapshot, so the nav bar visibly slid across
  on every navigation.

What replaced it (`src/layouts/Layout.astro`, inline `<style is:inline>`):

- Old page **accelerates out** — `translateX(-2.5%)` + fade to 0 over 200ms on
  `cubic-bezier(0.4, 0, 1, 1)` (ease-in: it is leaving, so it should start slow
  and leave fast).
- New page **eases in over it** from the right — 340ms on
  `cubic-bezier(0.22, 1, 0.36, 1)` (strong ease-out: fast off the line, soft
  landing). Longer than the exit so the two overlap and read as one gesture
  rather than two queued steps.
- The header carries `view-transition-name: site-header` and its group/pseudos
  are pinned with `animation: none`, so the nav holds still and only page
  content appears to move.
- The rules are **inline, not in the component `<style>`**: Astro extracts that
  to an external stylesheet, and a transition whose rules have not loaded yet
  falls back to the UA crossfade.

**Not implemented: direction-aware reversal.** Back/forward would push from the
opposite side, but Chrome does not fire a `navigate` event for browser-initiated
traversals (verified empirically — `history.back()` left `sessionStorage` and
the `NavigateEvent` log untouched). Making it reliable needs Astro's
`<ClientRouter />` and a direction attribute, which is a larger change than this
plan. The push is always forward until then.

### Findings considered, accepted, or refuted in this batch

- **`transition: all` on 11 sites** → HIGH; plans 011 + 012 together clear all
  11 (`grep -rn "transition-all" src/` must return nothing at the end).
- **Animating `box-shadow` on card hovers** (blog, RecentBlog, MarkdownPost,
  Works, PredirectDemo) → **accepted by design**: the offset hard shadow IS
  the brutalist hover signature; shadow-only transitions are paint, not
  layout. Plan 011 only scopes the property lists. Not to be "fixed" with
  pseudo-element shadow hacks without a new audit.
- **`@media (hover: hover)` gating** → **refuted for Tailwind utilities**:
  Tailwind v4 already wraps every `hover:` utility in `@media (hover:hover)`
  (verified in `dist/_astro/Footer.*.css`). Only raw `:hover` rules in
  `PredirectDemo.astro`/`CommandPalette.astro` component styles are ungated —
  accepted as LOW (palette trigger is `display:none` on mobile).
- **Command palette 180ms entrance** → kept: modals are the "occasional"
  frequency class and get standard motion; entrance already avoids `scale(0)`.
- **Keyboard-frequency rule** (no animation on keyboard actions) → not applied
  to palette open/close: it is a modal, not an instant toggle; the fix was the
  asymmetric *exit*, not removal (plan 014).
- **ScrollProgress bar animating `width`** → accepted: it is rAF-driven,
  scroll-linked indicator motion (constant-motion category), zero-dep, and
  already documented in the component.
- **Hero "open to work" ping** → kept (rare, meaningful status); the 7 rail
  pings deleted (plan 015).
- **Double-binding of `[data-copy-email]`** (Hero script vs CopyEmail script
  race) → pre-existing quirk noted in plan 016, explicitly out of scope.
